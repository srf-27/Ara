## 1. 约束与解法

| 约束 | 实际情况 | 处理 |
| --- | --- | --- |
| 用另一屏幕/桌面，不干扰用户 | 单屏 3200×2000、Session 1；用户正全屏运行游戏 | `CreateDesktopW` 建 `WinSta0\AraE2E3`，所有被测进程以 `STARTUPINFO.lpDesktop` 指向它；**全程未调用 `SwitchDesktop`** |
| codex computer use | Codex CLI 0.167.0，`computer_use` feature = stable；但 CUA 原生管道 `codex-computer-use-*` 不存在（Codex Desktop app 未运行），`node_repl` MCP 报 `Unsupported` | 启动 Desktop app 会弹到用户屏幕，违反约束。改用 `codex exec` 读图与出验收判定，配合隔离桌面内 `PrintWindow` 截图 + `PostMessage` 输入注入构成等价闭环 |
| 不弹 shell / 不弹 UAC | 当前会话 `IS_ADMIN=False`；UAC `ConsentPromptBehaviorAdmin=0`、`PromptOnSecureDesktop=0` | GUI 用不含外置 `.manifest` 的二进制副本，非管理员启动，无 UAC、无控制台窗口 |
| 测试脚本不能操作用户桌面 | 旧 `desk.py` 用 `pyautogui` + 全屏抓图，会抢焦点 | 全部弃用，改为文件 IPC 守护 + 窗口级操作 |

## 5. 缺陷清单（按严重度）

1. **`ara rooms` 硬编码 `ws://`**（`ara/src/main.rs:266`）→ 生产 WSS 部署下房间列表完全不可用，而同进程的 `up` 却正常。修复：仿照 `client::run`，按 access 文件里 `cert_pem` 是否为空决定 `wss://`，并复用 `ara::tls::client_config` 做 pin-by-root。
2. **GUI 单实例失效**（`ara-gui/src/main.rs:16`）→ 同一用户可开多个实例，可能重复建 TUN / 重复注册。修复：核查 `single-instance` 在 Windows 的命名互斥体作用域，改为显式检测并加回归测试。
3. **房间号可被任意占用**：`up --room <不存在的码> --password <任意值>` 会自动创建房间（旧 `cli-e2e-results.json` 的 `cli.up_bad_password` 曾拿到 VIP）。与「房间列表 + 密码二次验证才能进入」的设计有张力，建议明确禁止 join 时隐式创建。
4. **口径不一致**：房间列表显示 `0/8`（实时在线 peer 数），`ara-server list` 显示 `1 member`（持久化分配表）。数据不错，但 UI 文案建议区分「在线 / 已分配」。
5. **TUN 权限**：非管理员必然失败，属已知限制；`ara-gui.exe.manifest` 只在源码目录，未随 release 产物分发，实际安装时不会自动提权。

## 6. 未验收项与原因

GUI 视觉验收、GUI 真实点击流程、4 人全互通、切换房间二次确认、踢人客户端响应、文件断点续传 UI、虚拟网任意 TCP 中断恢复 —— 均未完成。原因：

- Windows 非活动 Desktop 不合成 GPU 窗口，任何 GDI 截屏 API 都拿不到 egui 内容；
- Codex 内建 window2 CUA 依赖未运行的 Desktop app，启动它会占用用户屏幕；
- 单机只有一个设备 ID，无法模拟真实多用户；TUN 需要管理员。

## 7. codex 验收判定（原文摘录）

```
Works: CLI core flows pass: setup, auth, create/list, join, file SHA256, kick, and help.
Works: Rooms state remains correct before/after creation, including the no-room.json IP-connect case.
Fails: rooms fails against WSS servers because it hardcodes ws://, causing an invalid HTTP version error.
Fails: TUN requires admin, and synthetic GUI input produced no server-side effect, leaving both paths unverified.
Risk: Production TLS/WSS room listing is broken until the hardcoded scheme is fixed.
Risk: Privileged TUN and GUI-input regressions may escape the current 14-case suite.
```

## 9. 下一步选项

- **A 零干扰继续**：保持独立 Desktop，给 GUI 增加可测试接口（状态导出/软件渲染开关）或改用 UI Automation，代价是需要改产品代码。

## 10. B 方案执行结果（用户批准短暂切换活动桌面）

用户选择「允许把隔离桌面切到前台完成 GUI 截图 + 点击验收」。共 **3 次成功切换**（`AraE2E5` / `AraE2E6` / `AraE2E7`），每次都用 `finally` + 独立 20 秒看门狗双重保证切回；另有 `AraE2E4` 一次因启动脚本用 `subprocess.Popen` 未指定 `lpDesktop`，在切换前就失败，用户桌面完全未动。

| 项 | 结果 |
| --- | --- |
| 切换与恢复 | 3/3 成功：`Default → AraE2Ex → Default`；`restored=true`，宿主 `OpenInputDesktop` 复查均为 `Default` |
| 用户桌面残留 | `FindWindowW("Ara")=0`，收尾后无残留 `ara-gui` / `ara-server` / python 进程 |
| 窗口级截图 | 切为活动桌面后由 13KB 白屏变为 58~61KB，可见标题栏、状态栏分隔线、左侧面板边界、输入框边线 |

| 点「加入 / 创建」后连服务器 | **未发生**：服务端日志只有 `ara-server listening on 23947`，`state-gui.json` 始终为 null |

**停止原因与可疑假设**：按坐标修正三次后仍未连上，停止继续切换（用户在游戏，不宜反复切屏）。最可能是键盘文字没进入 egui 控件（winit 在隔离桌面/合成焦点下的 `WM_CHAR` 处理），使 `connect()` 在 `self.create && self.password.is_empty()` 处提前返回；也可能是按钮坐标仍未命中。二者在不改产品代码、不增加可测试接口的前提下无法从截图区分。
